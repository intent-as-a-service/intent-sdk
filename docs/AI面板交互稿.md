## 0. 设计理念与不变式

**定位**：这不是"AI 能力菜单"，是**当前这件事的操作台**。菜单回答"系统有什么"，操作台回答"你现在该办什么、能不能一键办掉"。

### 0.1 起点：把不可靠的自然语言操作，换成可靠的意图

这个组件的出发点**不是"让 AI 聊天"**，而是三件事的规范化：

- **意图规范化**：每个能力声明成 `IntentSpec`——参数 Schema、上下文取值、输出 Schema、挂载点。用什么参数、能挂在哪个页面、产出什么结构，全是写死的。
- **执行规范化**：所有路径共用同一个执行器（工具白名单 + 出参校验 + 留痕 `traceId`），**不存在第二条"模型自由发挥"的路**。
- **事实规范化**：待办也是"意图 + 参数"，不是一段文案——增强器只能引用已登记的意图、只能传 Schema 里声明过的参数。

正因为有这三层规范化，"一键执行"才可信：参数不齐就要求补参，不会静默给一个似是而非的结果。

### 0.2 三级演进：从"用户点"到"系统提"

| 层级 | 谁先发起 | 系统的职责 | 现状 |
| --- | --- | --- | --- |
| **L1 用户点** | 用户明确知道要干什么 | 把参数补齐、把执行跑稳 | 已达成 |
| **L2 系统按上下文推荐** | 用户知道目标，但不确定该用哪个能力 | 用页面 + 对象 + 角色把候选排好序 | 进行中 |
| **L3 系统按事实主动提议** | 用户还没意识到有事 | 用业务事实（到期 / 欠款 / 未跟进）算出来，并说清理由 | 已起步（CRM 到期合同） |

层级越高，系统越"懂你现在准备做什么、可能还要做什么"。但**不变式不随层级改变**：无论哪一级，最终都必须落成一个合法的 `IntentRequest`。

### 0.3 三条不变式（后面所有设计不得违反）

1. **没有自由执行路径**：自然语言只充当"意图选择器 + 参数填充器"，产物必须是「意图 id + 合法参数」；不合法就回去补参，绝不直接执行。
2. **每个入口都要能说出理由**：对象（针对谁）+ 事实（为什么是现在）+ 来源（用户点的 / 上下文推的 / 事实算的 / 上一轮结果接力的）。说不出的，不许进首屏。
3. **推断只做排序，不做创造**：系统不能发明能力、不能创造参数，只能从已登记意图与已声明参数里挑。

### 0.4 三条设计原则

1. **准入三问**：一个入口要进首屏，必须同时满足「知道对象」「说得出为什么是现在」「一键能跑通」。缺一项降级到"更多能力"，缺两项就不该出现在这个面板里。
2. **按"离此刻多远"排序**，不按数据来源排序：刚跑完的接力 > 现在该办的待办 > 本页能办的意图 > 找不到就问（⑤ 意图路由）。
3. **首屏预算**：首屏可见行数 ≤ 8（不含输入框）。超预算一律折叠，不进首屏。

**术语对照**（界面用左列，右列是内部概念，不出现在界面上）：

| 界面文案 | 内部概念 |
| --- | --- |
| 接着干 | `followups` + `nextIntents`（上一次执行出参） |
| 现在该办 | `IntentSuggestion`（宿主 enricher 产出的确定性待办） |
| 本页能办 | 当前页面目录 `entries`（`IntentSpec.pages` 挂载） |
| 更多能力 | 全量可见意图（前端 `allEntries`） |

## 3. 组件级规格

### ① 上下文卡　[新增]

- **目的**：让用户一眼确认"这些建议是针对谁的"，并能在面板内换对象。
- **内容**：`对象名 · 对象类型`｜1 行关键事实（≤ 3 条，逗号分隔，取自 enricher 计数）｜数据新鲜度（"30 秒前更新"）。
- **交互**：`[切换对象 ▾]` 复用现有实体下拉（客户 / 合同）；切换后重置 ②③ 并重新拉目录。
- **空值**：没有对象时只显示页面名，不显示切换器。
- **埋点**：`panel_context_switch`。

### ② 接着干　[现状，仅改文案与位置]

- **出现条件**：仅本次会话执行成功后出现，与结果卡同生共死；**结果卡收起时仍然保留**（收起正文正是为了看下一步）。
- **内容**：`🔁 再改一版`（`followups` 3~5 条，点击把该句补进当前意图槽位重跑）+ `⭐ 接着办`（`nextIntents` ≤ 3 条，点击直达）。
- **准入**：引用的意图必须对用户可见，不可见的整条丢弃，不渲染灰按钮。
- **顺序**：再改一版在前（仍是当前意图，成本更低），接着办在后。
- **不显示 intentId**（研发可放在 hover 提示里）。

### ③ 现在该办　[改造：加对象级事实]

- **目的**：把"我的清单"升级为"当前这件事该办什么"。
- **准入**：沿用 SDK 现有准入（意图可见 + 参数在 schema 内声明 + item 型必填齐备），不合格整条丢弃。
- **展示**：按目标意图分组，**默认全部收起**，只显示「分组名 + 条数」；点开为表格（事项 / 操作两列），每组 5 条一页。
- **数量**：首屏最多 5 组，超出显示"另有 N 个分组（M 条）"。
- **排序**：与当前对象直接相关的组 → 我负责的全局待办 → 其余；组内按紧迫度（越早到期越靠前）。
- **失败态**：增强器失败**不许静默**——在该位置显示一行灰字"部分待办暂未取到（可重试）"，否则用户会误判成"没事可办"。
- **埋点**：`todo_group_expand`、`todo_item_run`（带 intentId 与来源分组）。
- **改动点**：`IntentCatalogContext` 增加当前对象与场景；缓存键从 `userId|page` 细化为 `userId|page|对象|场景`（现在的键会让不同对象串数据）。

### ④ 本页能办　[现状，收口]

- **目的**：承接"我知道要干什么、但懒得自己操作"。
- **展示**：最多露 3 个意图按钮（带一句 description），其余收进 `更多能力 ▸`。
- **顺序**：被宿主事实挂了徽标的意图优先（例如"5 份合同即将到期"那个），其余按声明顺序。
- **口径**：这里**只允许出现本页挂载的意图**。待办指向的非本页意图不进这里（否则用户会问"这入口哪来的"）。

### ⑤ 说一句 → 意图路由　[新增]

- **定位（重要）**：它是**路由器，不是自由执行入口**。输入框不产生新能力，只产生"同一批入口的另一种找法"；产物永远是「意图 id + 合法参数」，跟点按钮走的是同一条执行管线。这是 0.3 不变式 1 的直接落地。
- **目的**：吃掉长尾。用户的表达天然是句子，意图是枚举；用它把句子翻译成枚举，而不是拿句子去驱动执行。
- **交互**：输入 → 回车/点"跑" → 召回候选意图（Top 3）→ 抽参 → schema 校验 → 执行。
- **中间态**：候选置信度接近时列 3 个候选按钮让用户点选，不猜；选完仍走同一个槽位表单。
- **缺参**：复用现有 Schema 驱动槽位表单，不新做控件。
- **失败态**：没命中就给"没找到合适的能力"+ 2~3 个建议问法（取目录里热度最高的），**不要退化成自由回答**——用户来这里是办事，不是聊天。
- **安全**：不得因为走自然语言就绕过鉴权；命中意图同样要过"上架 + 角色"校验，参数同样要过 Schema 校验。
- **反例（不许做）**：把用户原话直接塞进某个"自由文本参数"然后执行；模型自己编一个意图 id；没命中却假装执行了。
- **埋点**：`ask_submit`、`ask_route_hit` / `ask_route_miss`、`ask_param_fill`。

### ⑥ 更多能力　[改造]

- **目的**：承接长尾能力检索，不占首屏。
- **展示**：默认收起；展开后按业务域分组（CRM / 合同 / 回款 / 系统…），顶部一个搜索框，走 name + description 匹配。
- **预算**：展开后仍需分页或虚拟滚动，不无限铺开。
- **取代**：现在的「意图菜单」平铺列表。

## 3.5 推断层：入口是怎么被推出来的（不是 UI，是决定上面内容怎么来的规则）

把"理解用户准备做什么"拆成**四个信号源**，各自产出「意图 + 参数 + 理由」，最后统一排序。所有信号源都不得绕过 0.3 的不变式。

| 信号源 | 输入 | 产出 | 层级 | 现状 |
| --- | --- | --- | --- | --- |
| 用户显式 | 点击 / 一句话 | 意图 id + 参数 | L1 | 已有 |
| 上下文 | 页面 + 当前对象 + 角色 + 场景 | 候选意图排序 | L2 | 部分（只有页面） |
| 业务事实 | enricher 查宿主业务库 | 待办条目（意图 + 参数 + 对象 + 理由） | L3 | 已有（CRM 到期） |
| 上轮结果 | `followups` / `nextIntents` | 接力条目 | L2/L3 | 已有 |

**排序公式（定性，避免拍脑袋）**：
`排序分 = 对象匹配权重 + 事实紧迫度权重 + 来源层级权重 - 已办/已忽略衰减`
- 对象匹配：条目所指对象 == 当前上下文对象 → 最高权重（这是 L2 的关键，也是目前最大的缺口）。
- 紧迫度：越接近到期/超期，排越前；同组内按时间升序。
- 来源层级：接力 > 事实待办 > 本页能力（离"此刻"越近越前）。
- 衰减：刚办过、刚忽略过的条目降权，避免反复打扰。

**三条红线**：
1. **可解释**：每个条目必须能渲染出一句"因为什么"（对象 + 事实 + 来源），前端不允许出现只有标题的入口。
2. **可回退**：推断错了，用户能一键换对象 / 换意图，不付出额外成本。
3. **不做创造**：信号源只能挑选与排序，不能新增能力、不能新增参数、不能编理由（理由只能来自业务事实）。

## 4. 状态与流转

| 状态 | 触发 | 面板表现 |
| --- | --- | --- |
| 加载中 | 打开面板 / 切对象 | 骨架屏保留区块占位，不闪空白 |
| 有待办 | 目录 `suggestions` 非空 | ①②③④⑤ 按序 |
| 无待办 | `suggestions` 为空 | 空态 D：给常用动作，不空白 |
| 增强失败 | enricher 抛异常 | ③ 位置显示降级提示，其余区块照常 |
| 执行中 | 点任一入口 | 入口置灰 + 结果区进度；布局不跳动 |
| 执行后 | 返回 SUCCESS | 结果卡（可收起）+ ② 置顶 |
| 执行失败 | 返回 FAILED | 错误卡 + 保留原入口可重试 |

**刷新时机（可验证的闭环）**：执行成功后后端已让该用户的目录缓存失效，前端应重新拉一次目录——办掉的那条待办要立刻消失。验收时专门测这一条。

## 5. 文案规范

- 分组标题用动词短语：`接着干` / `现在该办` / `本页能办` / `更多能力`。禁用"推荐""智能""意图"这类系统词。
- 每个待办条目的起因写**事实**，不写形容词：写"编号 HT-2026-0400 · 今天到期"，不写"该合同非常重要"。
- 按钮统一 `执行`；结果卡操作区保持现有 `复制 / 重新生成 / 👍 / 👎 / 执行过程`。
- 空态：`暂无待办。以下是你常对这个对象做的事：`，不写"暂无数据"。
- 加载态：不用整屏转圈，用区块骨架；超过 5 秒给"仍在计算…"。
- 失败态：给下一步动作（`重试` / `换个说法`），不给错误码。技术细节（traceId、错误码）折叠在"详情"里。

## 6. 排序与预算规则（可直接实现成代码常量）

1. 区块顺序：②接着干（有则置顶）→ ③现在该办 → ④本页能办 → ⑤说一句 → ⑥更多能力。
2. 待办分组排序：对齐 §3.5 排序公式——对象相关 > 我负责的 > 其他；组内按紧迫度升序（详见 §3.5）。
3. 本页能办：有徽标的优先，最多 3 个。
4. 预算：首屏 ≤ 8 行；待办 ≤ 5 组（每组 5 条分页）；接力 ≤ 3 条；本页意图 ≤ 3 个。
5. 折衷原则：预算不足时**宁少勿多**，被挤掉的内容进 ⑥ 或"另有 N 条"提示，不缩小字号塞进去。

## 7. 埋点与验收指标

- 北极星：**打开面板 → 一次执行成功的转化率**（不是意图数、不是曝光量）。
- 首屏效率：②③ 的点击占全站执行的比例，目标 ≥ 70%。达标说明"主动建议"这条路走对了，应继续加 enricher 规则而不是加意图数量。
- 输入框：提交率、路由命中率（`ask_route_hit / submit`）、无结果率。
- ⑥ 展开率：长期 < 10% 即确认它是辅助区，进一步弱化。
- 待办闭环：执行后该条待办消失的比例（应接近 100%）。

## 8. 不做清单（反模式）

对应 0.3 的三条不变式，这几件是明确不做的：

- **不新增自由执行路径**：用户原话不得直接当参数执行、不得绕过 Schema 校验；命中不了就说"没找到"，**不做自由回答兜底**。
- **不让模型创造**：模型不能自选意图 id、不能编参数、不能编推荐理由（理由只能来自宿主事实）。
- 不让 LLM 决定"展示哪些入口"（延迟 + 不可解释 + 每次不一样）；LLM 只用于"自然语言 → 意图 + 参数"。
- 不把全量意图平铺进首屏。
- 不做隐式批量执行；聚合型待办只呈现清单与数量，逐条办理。
- 不在执行中途整体重挂载面板（会清掉刚拿到的结果）。

## 9. 分阶段落地

| 阶段 | 层级 | 内容 | 依赖 |
| --- | --- | --- | --- |
| P0 | L1 打磨 | ①上下文卡（先只展示，不做切换）、③失败态可见、④收到 3 个 + 文案改动词 | 纯前端 |
| P0 | L2 | 上下文卡支持切换对象 | 前端 + `registerIntentPageContext` 支持多对象 |
