# 集成交付指南 —— 如何接入"旧业务系统"，改造量与解耦设计

> 版本 v0.1 · 配合《架构设计方案 v0.4》《功能清单》阅读
> 回答三个问题：集成到旧系统怎么做？改造量多大？面对未来各种系统如何规模化交付？

---

## 1. 先分清：演示页 ≠ 产品形态

MVP 里的 `intent-ui/index.html` 是**演示载体**，用来独立展示交互效果。
真正的产品交付物是 4 类**可嵌入件**（5 个 jar + 1 个 js），它们才是要集成进旧系统的东西：

| 交付物 | 形态 | 依赖 | 作用 |
|--------|------|------|------|
| `intent-spring-boot-starter`（jar） | Maven 依赖（**宿主只加这一个**） | Spring Boot + core/host/pi | 自动装配：REST API + 默认 SPI 实现 + 规则引擎接线，引入即用 |
| `intent-sdk-core`（jar） | Maven 依赖 | 仅 Jackson，**不依赖 Spring、不依赖 pi-java** | 意图执行引擎内核：规范加载校验、编排、目录装配、工具契约 |
| `intent-sdk-host`（jar） | Maven 依赖 | 仅 Jackson + core | 宿主 SPI（用户/权限/上下文/配置/仓储）+ **声明式事实规则引擎** + 一致性套件 |
| `intent-sdk-pi`（jar） | Maven 依赖 | pi-ai / pi-agent | 执行器实现：builtin-agent 推理循环、skill/flow 执行器、LLM 接入（**唯一依赖 pi 的模块**） |
| `yudao-module-intent`（jar） | 参考实现（宿主侧） | 宿主的安全/租户框架 | 把宿主能力接到 SPI 上（约 5 个类 + 若干 Bean），可当模板 |
| `intent-ui-sdk`（js + css，npm 包） | `<script>` 引入 / npm 依赖 | **无框架依赖**（原生 JS + CSS） | 悬浮入口 / 意图菜单 / 槽位表单 / 待办分组 / 结果卡 / 轨迹 / 历史 / 反馈，`IntentUI.configure()` 参数化后挂到任何页面；**后台 vben 已用它取代自研 Vue 面板（唯一实现，见第 6 节）** |

> 换宿主时**不需要照抄 300 行样板**：`intent-spring-boot-starter` 已覆盖装配，宿主只需按 SPI 提供 4 类 Bean（当前用户、权限判定、上下文桥接、配置状态）；`yudao-module-intent` 是这些 Bean 在若依生态下的一份参考实现。

演示页里 `demo-app.js`（假 CRM 页面）在真实交付中**不存在**——它的工作由旧系统自己的页面承担。

## 2. 集成到旧系统：三步标准动作

以 ruoyi-office 自带的 vben admin（Vue3）客户详情页为例：

### 第 1 步：后端（一次性，全局生效）

- `pom.xml` 加一个依赖：`intent-spring-boot-starter`（可按需再排除 `intent-sdk-pi`，纯流程型场景无需 LLM）；
- 按 SPI 提供 4 类 Bean：`IntentPrincipalProvider`（当前用户/租户）、`IntentPermissionPolicy`（权限判定）、`IntentContextBridge`（上下文 + 工具装饰）、`IntentConfigState`（上架开关，可给默认实现）；仓储默认内存实现，切文件/DB 换一个 Bean；
- 业务侧声明：宿主工具 Bean（`IntentTool`）+ `resources/intent/*.yaml`（意图）+ `resources/intent-rules/*.yaml`（事实规则）。

**改造量：0.5~1 人日**（不含梳理意图本身）。装配由 starter 承担，宿主代码只剩"把自家能力接到 SPI 上"；`yudao-module-intent` 是已跑通的一份参考实现（约 5 个类），可直接对照。

### 第 2 步：前端全局挂载（一次性）

```ts
// ① 引入：构建式宿主用 npm 包（后台 vben 就是这么接的，link: 指向唯一真源）
import { IntentUI } from 'intent-ui-sdk';
import 'intent-ui-sdk/css/intent-ui.css';
// 老页面 / 非构建式宿主：<script src="/intent-ui/js/intent-ui-sdk.js"></script>

// ② 注入宿主上下文（登录态沿用宿主会话，一行映射；实体下拉、层级可选）
IntentUI.configure({
  apiPrefix: '/admin-api/intent',
  authHeaders: () => ({
    Authorization: 'Bearer ' + userStore.accessToken,
    'tenant-id': tenantStore.getTenantId,
  }),
  entityOptions: { customerId: () => api.get('/crm/customer/simple-list') },
  zIndex: 900,
});

// ③ 全局入口（悬浮球 + 抽屉），所有页面共享：
IntentUI.mountFloating({
  getPage: () => route.path.replace(/^\//, ''), // 页面标识 → 按页面装载意图
  getContext: () => pageContext(route),         // 当前页面能提供什么上下文
});

// 需要内嵌在某块区域（调试台 / 侧栏）时改用：
IntentUI.mount({ container: el, page: 'crm/contract', mode: 'debug' });
```

**改造量：0.5~1 人日**。登录态完全沿用宿主现有会话，无独立登录、无跨域、无权限改造。

### 第 3 步：页面级上下文（每个页面 ~5 行）

```ts
// 业务页面：声明"本页能提供什么上下文"，面板打开时按当前页面取用
registerIntentPageContext('crm/customer', () => ({
  customerId: currentCustomerId.value,      // 来自页面可见数据，保证面板与页面一致
  customerName: currentCustomerName.value,
}));
```

**改造量：每页 10 分钟**。真正的实施工作量不在代码，在**梳理意图**（见第 4 节 SOP）。

### 对老技术栈（JSP / jQuery / 服务端模板）同样适用

`intent-ui-sdk.js` 是原生 JS：`<script>` 引入 + 一个 `<div id>` + 一段 mount 调用。
连模板都改不了的系统，走第 5 节的"网关/注入"模式。

## 3. 解耦度论证（当前架构已经隔离了什么）

| 边界 | 证据 |
|------|------|
| SDK 不绑定宿主框架 | intent-sdk-core / intent-sdk-host 无 Spring 依赖；上下文桥接与权限判定由宿主实现 SPI 提供 |
| SDK 不绑定 AI 引擎 | pi-ai / pi-agent 只出现在 `intent-sdk-pi`；工具契约是 SDK 自有的 `IntentTool`，`PiToolAdapter` 是唯一转换点——换引擎只换一个模块 |
| 规则与代码解耦 | 事实规则写在 YAML（查询 + 条件 + 模板 + 参数映射），改文案/阈值/挂载页面不用改 Java、不用发版 |
| 平台与业务解耦 | 业务模块（crm）只有声明（1 个配置类 + 3 个 YAML + 1 个 pom 依赖）；删掉 crm，意图平台照常运行（只是没有意图） |
| 网关可组装 | `intent.gateway.enabled=false` 时全部功能可用（仅 remote 意图降级）；M2 装上即解锁跨系统 |
| 前端框架无关 | intent-ui-sdk 原生 JS（`IntentUI.configure` 参数化 apiPrefix/鉴权/文案/层级/实体下拉），Vue2/Vue3/React/jQuery 通用；后台 vben 与演示页共用同一份文件 |
| 模型供应商可替换 | LlmConnector 的 StreamFn 注入点 + 配置化 provider，换 LLM 不改代码 |
| 多方言可部署 | 建表脚本按库分目录：`deploy/sql/{mysql,postgresql,oracle,sqlserver}`；或走零建表文件模式（File 仓储） |
| 登录态零改造 | 组件复用宿主 token（同源），不建独立账号体系 |
| 权限事务零改造 | 工具进程内直调宿主内部 SDK/API，权限与事务随宿主调用栈 |

## 4. 规模化交付体系（面对未来各种系统）

### 4.1 三级接入模式，按系统可改造程度选择

| 模式 | 适用系统 | 系统侧改造 | 平台侧工作 | 能力 |
|------|----------|-----------|-----------|------|
| **A · SDK 嵌入**（首选） | Java 系自研系统（可改代码） | 引 starter + 4 个 SPI Bean + 工具/YAML 声明 | 0（自助） | 全能力：本地闭环、权限事务沿用宿主、数据不出域 |
| **B · 网关接入** | 非 Java 系统（.NET/PHP/Go），或不愿嵌 SDK | 暴露一组**普通 REST API** + 意图接口薄层（约 1~3 天） | 连接器适配 2~5 天/系统 | 跨系统编排、短时凭证、统一审计；无本地 AI |
| **C · 连接器代管** | 完全封闭/不可改造系统 | **零改造**（有可用 API 或只读库即可） | 平台写连接器 3~5 天/系统 | 仅查询类意图；凭证由平台托管 |

M1 已落地 A；B 的客户端契约已实现（intent-sdk-gateway）；C 为 M3。

### 4.2 单系统实施 SOP（可复制的方法论）

| 阶段 | 动作 | 产出 | 人日 |
|------|------|------|------|
| ① 意图调研 | 和业务方过高频场景，圈定 3~5 个 L1/L2 意图 | 意图菜单表（id/名称/参数/上下文/页面挂载点） | 1~2 |
| ② 平台装配 | 引 starter、实现 4 个 SPI Bean、配 LLM/留痕/网关开关 | 意图 API 可用 | 0.5~1 |
| ③ 工具包装 | 每个意图 1~3 个宿主工具（内部 SDK/API → `IntentTool`） | 工具 Bean | 0.5/个 |
| ④ 意图定义 | IntentSpec YAML（模板 + 沙箱调试器调提示词） | 通过校验的规范 | 0.5/个 |
| ⑤ 前端挂载 | 全局入口 + 页面上下文 | 页面出现意图按钮 | 0.5~1 |
| ⑥ 评测基线 | 每个意图录 3~5 个 golden case，跑沙箱回归 | 评测集 | 0.5/个 |

**典型首系统落地：5~8 人日**；后续每新增一个意图 1~1.5 人日；新增一条事实规则 0.5 人日（写 YAML）；每个新系统（模式 A）边际成本递减（装配已由 starter 承担，宿主只需接 SPI）。

### 4.3 版本、发布与升级策略

- SDK 独立版本号（`dev.intent:*:0.1.0-SNAPSHOT`），宿主按需升级；意图 YAML 与规则 YAML 随业务模块走，与平台版本解耦；
- **发布制品**：`mvn install/deploy` 同时产出 jar + `-sources.jar` + `-javadoc.jar`（3 个插件已配置）；`-P release` 挂载 GPG 签名；LICENSE 为 Apache-2.0，父 pom 已声明 licenses/developers/scm，具备上中央仓库（或私服 Nexus）的条件；
- **依赖分层是升级的护栏**：宿主只依赖 `intent-spring-boot-starter`，pi-ai/pi-agent 藏在 `intent-sdk-pi`；升级 pi 不影响宿主契约，反向升级 SDK 也不会把 pi 强加给宿主（可 `exclusion` 掉 pi 走纯流程型）；
- 规范校验是升级安全网：SDK 升级后启动即校验全部意图与规则，不兼容立即暴露（启动失败 > 运行期静默出错）；
- 一致性套件 `IntentHostConformance`：宿主接入自测（权限、上下文、仓储、规则），升级后跑一遍即知有没有踩到契约变化；
- 留痕 JSONL → 数据库（M2）接口不变，宿主无感。

## 6. vben 集成实录（已完成：SDK 唯一实现）

### 集成模式

后台不再自己实现一遍意图面板。悬浮球 / 抽屉 / 意图菜单 / 槽位表单 / 待办与推荐（分组 + 分页）/
结果卡片（可收起）/ 执行轨迹 / 历史 / 反馈，全部来自 `intent-ui-sdk.js`，宿主只留**薄适配器**：

- **唯一入口**：登录后所有页面右下角一个可拖动的 AI 浮标（位置记在 localStorage，刷新保持）；
- **按页面装载**：页面标识 = 当前路由路径（如 `crm/customer`），目录接口按 `?page=` 过滤，与 IntentSpec 的 `pages` 挂载声明匹配；`pages` 未声明 = 全局意图；
- **未配置提示**：页面无可用意图时显示引导（后台配置保存后即时生效，无需发版）；
- **页面上下文注册**：业务页面调用 `registerIntentPageContext('crm/customer', () => ({ customerId, customerName }))` 声明上下文来源（取自页面可见数据，保证面板与页面数据一致，杜绝"张冠李戴"）；
- **行级入口**：`openIntentDrawer('crm/customer')` 可按指定页面强制装载（列表页的行级按钮已按产品决策撤掉，能力保留）。

分层原则——**SDK 管交互，宿主管运营**：

| 层 | 归属 | 说明 |
|------|------|------|
| L1~L2 交互层 | `intent-ui-sdk.js` | 一个文件所有宿主共用；改交互只改这一份，后台 / 演示页 / 其它宿主同步生效 |
| 宿主适配 | `views/intent/{sdk.ts, components/IntentFloating.vue, pageContext.ts}` | 约 120 行，只有"注入 + 挂载"，没有渲染逻辑 |
| L3~L4 运营端 | `views/intent/{config, executor, center}` | 意图上架 / 执行器档案 / 调试台——宿主侧管理界面，不属于嵌入式组件 |

### 接入方式：npm 依赖指向唯一真源（零拷贝）

```json
// apps/web-antd/package.json
"intent-ui-sdk": "link:../../../ruoyi-office/yudao-module-intent/src/main/resources/intent-ui"
```

`link:` 指向的就是后端模块里的静态资源目录——它同时是演示页、`<script>` 交付形态和 npm 包的
**同一份文件**（该目录已带 `package.json`、ESM 入口 `js/intent-ui-sdk.mjs`、类型声明 `js/intent-ui-sdk.d.ts`）。
好处：改 SDK 立刻在后台 HMR 生效，不会出现"两份实现漂移"。对外交付时把 `link:` 换成版本号即可。

> `vite.config.mts` 需声明 `server.fs.allow`：Vite 一旦显式设置该字段就会**覆盖**默认值（工作区根），
> 所以既要放行 SDK 真源目录，也要写回 `searchForWorkspaceRoot(process.cwd())`。

### 验证结果（本轮实测：无头 Edge 1560×880 · 真实后端 + 真实 LLM）

## 7. 目录增强接入（可选）：让意图入口说业务话

默认形态下，意图入口对每个用户、每个时刻都是同一组按钮（「分析此客户」「生成跟进方案」）。**目录增强**让入口带上业务事实与待办清单：同一颗 AI 图标，打开就是「合同「金辉电子 MES 运维续约合同」还有 5 天到期 · 点击一键做风险审查」——入口从"能力列表"变成"待办列表"。

### 接入成本：一条规则一份 YAML（零 Java）

| 步骤 | 动作 | 位置 |
|------|------|------|
| 1 | 实现 `IntentFactProvider`：提供数据集（只取数，复用宿主既有 Service/Mapper，口径与页面「待办事项」一致） | 业务模块，如 `yudao-module-crm/.../crm/intent/CrmIntentFactProvider.java` |
| 2 | 写规则 YAML：一条规则 = 查询 + 条件 + 输出模板 + 参数映射 | 业务模块 `resources/intent-rules/*.yaml`（或 `intent.rules-dir` 指向外部目录） |
| 3 | 无。SDK 自动装配、自动缓存与失效；前端一次实现，后续所有规则复用 | — |

```yaml
# yudao-module-crm-server/src/main/resources/intent-rules/crm-contract-expiring.yaml
- id: crm.contract.expiring
  intent: crm.contract.risk-review          # 目标意图（必须已注册，否则启动失败）
  dataset: crm.expiring-contracts           # 事实来源（上一步提供的数据集）
  scope:
    page: ["crm/*", ""]                     # 只在这些页面提示，避免系统管理页打扰；空串 = 意图中心
  badge:
    text: "{{count}} 份合同即将到期"          # 意图按钮上的事实徽标
    level: warning
  items:
    limit: 5
    title: "合同「{{row.name}}」{{row.endTime | expiryText}}"
    subtitle: "编号 {{row.no}} · 点击一键做风险审查"
    reason: "我负责的合同临近到期，建议提前审查履约与续约风险"
    params:                                 # 参数映射：必须是该意图已声明的入参
      contractId: { from: row.id, type: string }
      focus: { value: "到期与续约风险" }
```

改文案、改阈值、改挂载页面只动这份 YAML；规则在**启动时校验**（意图不存在、参数不在入参 Schema 内 → 服务直接起不来），不会静默失效。多模块的事实源由 `CompositeIntentFactProvider` 聚合并按数据集名分发。规则表达不了的复杂逻辑仍可实现 `IntentCatalogEnricher`（`intent-sdk-core`）作为逃生舱，两者可并存。

### 三条边界（SDK 已强制，宿主不必自己防）

- 徽标只挂当前页面已装载的意图；建议引用的意图必须在用户可见集合内，否则整条丢弃；
- 建议 `params` 必须在意图参数 Schema 内、条目型建议的必填参数必须齐备——不会出现"点了报缺参"的死入口；
- 事实求值是同步的：只做轻量查询（计数 / 近 N 条），单个事实源异常被隔离，目录接口不因此失败。

### 配置（宿主 `application-local.yaml`）

```yaml
intent:
  suggestions:
    enabled: true
    max: 5            # 每条业务规则最多返回几条建议（各规则配额独立，互不挤占）
    cacheSeconds: 30  # 宿主侧缓存；意图执行成功后该用户缓存立即失效
  rulesDir:           # 可选：外置规则目录（jar 内 classpath*:intent-rules/*.yaml 之外再加载一份，
                      # 运维改文案/阈值不必重新打包；与内置规则同名同 id 时以外置为准）
```

### 实测（ruoyi-office + vben）

规则全部改为声明式后实测（ruoyi-office + vben，规则文件 `crm-contract-expiring.yaml`）：

| 场景 | 结果 |
|------|------|
| `GET /intent/catalog?page=crm/contract` | 意图按钮带徽标「5 份合同即将到期」(warning / count=5)，并返回 5 条建议（各含 `contractId` / `focus`） |
| 同上，建议文案（模板渲染实测） | 「合同「华宇置业智能楼宇运维合同」还有 4 天到期（2026-09-18）」/「合同「天诚物流 TMS 年度运维合同」**今天到期**」（`expiryText` 过滤器按剩余天数换文案） |
