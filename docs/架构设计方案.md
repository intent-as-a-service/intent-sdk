# 统一意图网关平台 · 架构设计方案

> 版本：v0.4（待确认） 日期：2026-09-10
> 状态：架构设计稿。已确认：**嵌入式 AI（原生 SDK 进程内）**、**网关为可组装项（非必须）**、**网关统一换发短时凭证**、**本地工具直调宿主内部 SDK/API**、**第一步 Java MVP（基于 pi-java harness）**。含设计图 3 张。

---

## 1. 背景与目标

前期已确定的产品思路：**去聊天框，"意图即服务"**——在业务系统界面上以"意图按钮"替代 AI 对话框，把高频任务固化为结构化意图，点击即执行，结果以卡片/表单内嵌回业务界面（L1 快捷指令 / L2 智能操作 / L3 自动化流程）。

本方案叠加以下已确认决策：

1. **嵌入式 AI，原生 SDK**：AI 能力以宿主语言原生 SDK 进程内嵌入各业务系统，点击意图优先**本系统内闭环完成**（LLM 推理 + 工具调用 + 返回结果）；
2. **本地工具直调宿主内部 SDK/API**：以当前登录用户上下文在宿主系统内执行，**权限与事务天然沿用宿主系统**，零权限改造、无分布式事务；
3. **网关是可组装项，不是必须项**：不装网关，SDK 照常完成业务处理——但只能在本系统上下文内；装上网关，才具备**路由到其它系统**处理跨系统意图的能力。架构随网关 presence 优雅降级；
4. **网关统一换发短时凭证**（启用网关时）：跨系统调用由网关签发短时凭证，目标系统本地校验后映射为用户身份执行；
5. **意图规范化（核心）**：输入、执行、输出均有 Schema 约束，执行路径确定、结果可校验、质量可评测；
6. **第一步：Java MVP**，基于现有 `pi-java` harness（pi-ai + pi-agent）构建内嵌 AI SDK，以 Maven jar 形态集成进业务系统。

### 一句话定位

> **内嵌 AI SDK（必备）+ 意图网关（可组装）**：SDK 让每个业务系统成为自治意图节点（本地上下文内闭环）；网关是节点间的可选互联总线，装上即得跨系统意图路由。

## 3. 总体架构

总体架构见 `docs/diagrams/01-总体架构图.png`。三个组成部分，按"必备 → 可组装 → 可后置"分层：

### 3.1 内嵌 AI SDK（必备内核，每个业务系统集成）

以宿主语言原生 SDK 进程内运行（Java MVP），包含：

- **意图组件 SDK**（UI 层）：意图菜单/按钮渲染、页面上下文采集、结果卡片渲染；
- **意图分析器**：点击意图后判断执行位置——scope 声明为主 + 上下文复核；**未装配网关时恒为本地**（scope=remote 的意图明确提示不可用，不静默失败）；
- **LLM 执行引擎**：推理、工具调用、Prompt 模板，输出经出参 Schema 校验后返回；
- **本地工具集**：直接封装宿主系统的**内部 SDK 与内部 API**，进程内调用——权限与事务天然沿用宿主系统；
- **意图接口（Intent API）**：本系统对外暴露的意图服务端点——仅在装配网关（或需要被其它系统调用）时启用，被调用时等同于一次"本地执行"。

### 3.2 意图网关（可组装，可选）

独立可选组件，装配后解锁跨系统意图：

- **意图目录与路由**：哪个系统注册了哪些可跨系统调用的意图，按 intent_id 路由；
- **身份信任传递**：校验来源后**统一换发短时凭证**（映射身份、来源系统、调用链 ID、短有效期），目标系统校验后映射为本地用户上下文执行；
- **调用治理**：熔断、限流、协议适配（标准 IntentRequest/IntentResult）；
- **全链路审计**：跨系统调用链留痕。

> **降级语义**：SDK 通过 SPI 探测网关装配状态。`scope=local` 意图在任何部署形态下行为一致；`scope=remote/composite` 意图仅在装配网关后可用/完整可用。

### 3.3 意图注册与配置中心（可后置，全公司共享时引入）

意图注册中心（IntentSpec + scope）、后台配置管理（自助新增/发布）、身份与信任管理（网关模式）、评测反馈库。MVP 阶段意图配置随宿主本地存放（classpath/DB），引入配置中心后统一下发。

## 4. 内嵌 AI SDK 设计（Java MVP，基于 pi-java harness）

### 4.1 为什么基于 pi-java

`D:\project\myopensource\pi-agent\pi-java` 是 pi 编码代理核心的 Java 21 移植版：仅依赖 Jackson，HTTP/SSE 用 JDK 内置 `java.net.http`，344 个测试用例，质量与依赖干净度适合进业务系统 classpath。其分层与本方案高度同构：

| pi-java 能力 | 在内嵌 SDK 中的角色 |
|---|---|
| `pi-ai` `Models` / `Model` / `streamSimple` | **模型接入层**：统一流式 API，内置 Anthropic / OpenAI / Google / Bedrock / Azure / Mistral / OpenRouter 等 9 种协议适配 + 自定义端点注册（PI_BASE_URL 方式接 vLLM/GLM 等） |
| `pi-ai` `Schema` + `ToolValidator` | **参数规范**：IntentSpec 参数 JSON Schema 声明与入参校验（复用/扩展出参校验） |
| `pi-ai` `Message` / `ContentPart` / `AssistantMessageEventStream` | 消息模型与流式事件（卡片流式渲染的数据源） |
| `pi-agent` `AgentTool`（name/description/parameters/execute） | **工具执行形态**：SDK 不直接暴露该接口，而是定义自有 `IntentTool`（同形契约），由 `intent-sdk-pi` 的 `PiToolAdapter` 单向适配进 pi 的执行循环 |
| `pi-agent` `AgentLoop` / `Agent` | **意图执行引擎的推理循环**：顺序/并行工具执行、steering/followUp、before/after 钩子（挂审计）、失败截断 |
| `pi-agent` `AgentHarness` + `SessionTree`/JSONL 会话 | **执行留痕**：每次意图执行持久化转录，可回放可审计（可信四道防线之二） |
| `pi-agent` harness `PromptTemplate` / `Skill` | 意图 Prompt 模板与编排说明挂载 |
| `pi-agent` `compaction` | 长会话/长编排上下文压缩 |
| `StreamFn` 注入点 | 模型供应商解耦：换模型/接企业网关不改 SDK |
| `pi-protocol` / `pi-server` / `pi-client` | （可选）意图接口 RPC 化、远程调试通道 |

### 4.3 意图执行的关键机制

- **意图 ≠ 聊天**：点击意图是确定性调用——参数来自表单 + 页面上下文，无需 LLM 选工具；LLM 的职责是在编排步骤内做推理与工具调用。内置 `AgentExecutor` 构造 `Context`（意图模板为 system prompt）并驱动 `AgentLoop`；
- **契约与执行解耦（Executor SPI）**：`IntentRuntime` 只做通用编排（校验/路由/规范化/留痕），执行内核是可替换的 `IntentExecutor`——意图规范用 `executor: <id>` 声明由谁执行，缺省 `builtin-agent` 推理循环。执行器本身支持声明式档案（`ExecutorProfile`：type / model / 工具白名单 / limits，YAML 加载、`ExecutorProfiles.build` 构建——每个执行器绑定独立模型，执行器白名单是能力上限，意图白名单在其内收窄）；手写 `IntentExecutor` 实现经 `IntentRuntimeConfig.customExecutors` 注册即可接入工作流引擎、规则引擎、多智能体编排等执行方式，意图契约恒定不变。执行器未注册时意图不可执行：运行时报 `EXECUTOR_NOT_FOUND`，管理端保存意图时经 `IntentSpecValidator.validate(spec, runtime.executorIds())` 与槽位校验同级拦截错配；
- **agent 型与 skill 型的分工**：agent 型把"怎么做"交给模型现场规划（工具集 + 推理循环，灵活但耗 token）；skill 型把"怎么做"固化为 steps 流程——工具步骤直调宿主工具、LLM 步骤单次推理，`${...}` 模板串联步骤上下文（`params` / `context` / `steps.<name>.text`），出参按模板组装并经 Schema 校验。纯工具技能零 LLM 即可运行，适合标准作业程序（如"标准催收七步法"）；
- **上下文即参数**：业务页面已定位对象时（如客户列表页注册 `{customerId}`），页面上下文自动补全缺失的必填参数——意图点击即执行，无需用户重复填写；仅在上下文也无法提供时才弹出补全表单（NEED_INPUT）；
- **宿主工具**：业务开发者只需写一个类（实现 SDK 自有契约 `IntentTool`）包装内部调用，Schema 声明参数——权限与事务随宿主调用栈自然生效（执行器经 `HostContextBridge` 装饰器把登录用户/租户恢复到工具线程）；
- **执行留痕**：每次执行（无论成败）由 `IntentRuntime` 写入 `TraceStore`（`ExecutionTraceRecord`：参数、输出、错误、每步轨迹）——内存 / JSONL 文件 / 数据库实现可替换，对应审计与回放；不装配则不落盘；
- **可信兜底**：入参校验失败 → 拒绝执行返回表单；出参校验失败 → 重试一次 → 降级人工表单；
- **模型接入**：`StreamFn` 注入 + `Models.registerCustomStream`，MVP 用环境变量/配置接企业认可的端点（如 PI_BASE_URL 方式），供应商可替换。

### 4.4 目录增强（宿主事实驱动的提示与建议）

目录接口默认只回答"这个页面有哪些意图"。**目录增强**让宿主用自己的业务事实，把"有哪些意图"升级为"现在该办哪件事"——例如「你的 3 个客户本月未跟进」（点击直跑跟进方案）、「2 份合同即将到期」（一键风险审查）。全程确定性求值，不经过 LLM，因此可缓存、可解释、可测。

| 能力 | 协议字段（intent-protocol） | 前端渲染位置 |
|------|------------------------------|--------------|
| 提示徽标 badge | `IntentCatalogEntry.badge = {text, level, count}` | 意图按钮上的等级色 Tag（info / warning / danger） |
| 个性化建议 suggestion | `CatalogResponse.suggestions[] = {id, intentId, title, subtitle, kind, count, params, reason, dedupKey}` | 统一「下一步」区（执行前叫「待办与推荐」）：按目标意图分组、每组默认 3 条可展开，点击即执行 |

宿主接入有**两条路**，默认走声明式，写不动规则的场景才落到 Java。

**① 声明式事实规则（推荐，零 Java）**：一条规则 = 查询 + 条件 + 输出模板 + 参数映射，放在业务模块的 `resources/intent-rules/*.yaml`，或由 `intent.rules-dir` 指向外部目录（运维改文案不用重新打包）：

```yaml
- id: crm.contract.expiring
  intent: crm.contract.risk-review          # 目标意图（必须已注册，否则启动失败）
  dataset: crm.expiring-contracts           # 事实来源（宿主 IntentFactProvider 提供）
  scope:
    page: ["crm/*", ""]                     # 只在这些页面提示；空串 = 意图中心
  badge: { text: "{{count}} 份合同即将到期", level: warning }
  items:
    limit: 5
    title: "合同「{{row.name}}」{{row.endTime | expiryText}}"
    subtitle: "编号 {{row.no}} · 点击一键做风险审查"
    reason: "我负责的合同临近到期，建议提前审查履约与续约风险"
    params:
      contractId: { from: row.id, type: string }
      focus: { value: "到期与续约风险" }
```

宿主只提供**事实**：实现 `IntentFactProvider`（一个 `crm.expiring-contracts` 数据集，复用宿主既有 Service/Mapper 查询，口径与页面「待办事项」一致）。规则引擎负责条件求值、模板渲染与参数映射，`CompositeIntentFactProvider` 负责多模块事实源聚合分发。

**② Java 增强器（逃生舱）**：规则表达不了的复杂逻辑，仍可实现 `IntentCatalogEnricher`（`intent-sdk-core`），声明为 Bean 即被装配；能力与声明式规则等价，可与规则并存。

```java
@Component
public class CrmIntentCatalogEnricher implements IntentCatalogEnricher {
    @Override public Map<String, IntentBadge> badges(IntentCatalogContext ctx) { ... }     // 意图按钮上的事实徽标
    @Override public List<IntentSuggestion> suggestions(IntentCatalogContext ctx) { ... }  // 逐条待办 + 可直接执行的参数
}
```

准入与隔离由 SDK 统一把关（`IntentCatalogAssembler`），增强器只负责"提供事实"：

- 徽标只允许挂在**当前页面目录里已装载**的意图上（页面上没有的按钮不出现提示）；
- 建议引用的意图必须在**用户可见意图**集合内（已上架 + 角色匹配），且 `params` 必须命中该意图已声明的参数、条目型建议的必填参数必须齐备——不合格的建议被丢弃，不会渲染出点不动的入口；
- `aggregate` 型建议只呈现待办清单与数量，需逐条办理，不做隐式批量执行；
- 单个增强器抛异常只影响它自身（逐个隔离降级），目录照常返回；
- 条数上限按增强器（每条业务规则）**独立计算**——一条规则条目再多也不会挤占其他规则的配额；前端按目标意图分组、默认全部收起，条目多也不至于刷屏；
- 结果按用户缓存（`intent.suggestions.cacheSeconds`），意图执行成功后自动失效该用户缓存，办完事入口即时刷新。

**前端交互（一次实现，对所有规则生效）**：执行前/执行后共用同一个「下一步」卡片，执行后标题切为「下一步」，按来源分三组，自上而下依次是——补充要求重跑（LLM 出参 `followups`，仍是当前意图，点击把该句补进槽位重跑）、AI 推荐意图（LLM 出参 `nextIntents`，指向另一个意图）、宿主待办（业务事实，执行前已算好，与本次执行无关）。越贴近本次结果的分组排得越靠前，宿主待办放最后，避免把刚跑完的相关入口顶下去；三个来源统一入口、视觉同构，用户只需往下看一次。

`followups` / `nextIntents` 由 LLM 在 `submit_result` 里给出，提示词层已明确约束（`AgentExecutor` 系统提示 + `IntentSpec` 字段描述）：`nextIntents` 的 `intentId` 必须取自「可推荐的下一步意图目录」；`followups` 给 3~5 条、每条一句话且可直接执行、不复述 summary 的结论，确实没有才留空数组。实测同一意图连续 8 次执行有 7 次输出 4~5 条（改造前 12 次里只有 6 次带 `followups`）。

宿主待办在「下一步」卡片里再按目标意图分组：**最多并列 5 个分组，每组默认收起**，只显示「📌 待办 · 分组名 + 条数」，点开才展开成一个表格（事项 / 操作两列，说明与起因并入事项单元格）。抽屉只有 460px 宽，不做横向铺开；组内超过 5 条自动分页；分组超过 5 个时其余收成一行「另有 N 个分组（M 条）未展示」提示。

**扩展成本**：新增一条业务规则 = 新增一份 YAML（约 20 行，改文案/改阈值/改挂载页面只动它）+ 一个取数用的数据集实现；SDK 与前端一次性实现，后续规则零改前端、零改 Java。规则在启动时校验（意图不存在、参数不在入参 Schema 内立即失败），不会静默失效。

### 4.5 MVP 范围与验收（Java）

**做**：`intent-protocol` + `intent-sdk-core` + 一个 demo 宿主（模拟 CRM）。
**验收场景**（无网关，全链路本地）：
1. demo 宿主注册 3 个意图：纯本地分析（L1）、多工具编排（L2，直调宿主内部 API）、缺参回填表单；
2. 点击意图 → 分析（恒本地）→ LLM 推理 + 工具调用 → 出参校验 → 卡片结果渲染；
3. 执行转录 JSONL 落盘，可回放；
4. `scope=remote` 意图在无网关时给出明确不可用提示。

**不做**（下一里程碑）：网关模块与跨系统路由、配置中心、多语言 SDK、UI 组件产品化。

## 5. 意图规范 IntentSpec（方案核心）

每一个意图是一份结构化规范文档，五要素齐备才可发布。数据模型见 `docs/diagrams/03-意图规范与生命周期.png`：

| 要素 | 内容 | 规范化带来的确定性 |
|------|------|--------------------|
| ① 标识与元数据 | 全局唯一 `intent_id`（命名空间 `系统.域.动作`）、名称、描述、负责人、版本、状态 | 路由唯一、权责清晰、可灰度回滚 |
| ② 输入规范 | 参数 JSON Schema + 上下文声明（需要哪些页面实体） | 入口是"选择题"，入参 100% 可校验 |
| ③ 执行编排 | **scope：本地 / 远程 / 组合**；步骤 DAG：`ai` / `api` / `tool` / `condition` / `human` | 分流有据；执行路径可测试、可回放、可审计 |
| ④ 输出规范 | 结果 JSON Schema + 渲染契约（卡片/表单类型） | 结果机器可校验，本地与远程返回同构 |
| ⑤ 治理策略 | 可用角色、限流、审计级别、失败兜底、评测用例集 | 质量有基线，发版可回归评测 |

**规范化 → 可信**：入口校验 → 分流有据 → 执行留痕 → 输出校验（不过重试/降级表单）→ 反馈回流评测。

## 6. 核心流程

### 6.1 意图执行流（运行时）

时序见 `docs/diagrams/02-意图执行时序图.png`：

1. 用户点击意图菜单，SDK 提交 `intent_id + 参数 + 页面上下文`；
2. **意图分析器判断执行位置**（scope 为主 + 上下文复核；无网关恒本地）；
3. **分支 A · 本地意图**：`IntentRuntime` 驱动 AgentLoop → 工具直调宿主内部 SDK/API（权限事务沿用宿主）→ 出参校验 → 卡片渲染；
4. **分支 B · 跨系统意图（需网关）**：提交网关 → 换发短时凭证 → 路由到目标系统意图接口 → 目标系统以同一套 SDK 本地执行 → 结果原路返回；
5. 执行转录留痕；Trace 与反馈异步回流评测库。

### 6.2 意图配置流（管理态）

新建（规范表单）→ 测试（沙箱 + 评测回归）→ 发布（MVP 随宿主本地装载；后期配置中心统一下发，零发版生效）→ 监控 → 迭代/下线。
