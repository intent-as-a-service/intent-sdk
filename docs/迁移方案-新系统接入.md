# 迁移方案 —— 把「意图即服务」搬进一个新业务系统（Vue + Spring Boot）

> 目标读者：准备把本能力接入另一套自研业务系统的架构师 / 开发。
> 结论先行：**能迁，而且不用重写内核**。真实工作量 = 一次性搬 400~800 行「宿主适配层」+ 每个意图约 60~90 行声明式配置。

## 0. 一句话结论

迁移 = **复用 6 个 SDK 模块（零改动）** + **参考改写一个「宿主适配层」（一次性，400~800 行）** + **声明式写业务（每意图 1 份 YAML + 若干工具）**。

**不要**「复制整个 ruoyi-office 改包名」——那会把 yudao 的框架耦合（CommonResult、MyBatis、Security、Tenant）一起搬过去，新系统的技术栈未必对得上，而且内核升级要人工 merge。

## 1. 现状分了几层（决定「哪些能直接拿」）

| 层 | 现在放在哪 | 规模 | 迁移属性 |
| --- | --- | --- | --- |
| L1 执行内核 | `next-agent`（6 个 Maven 模块） | 6 模块 / 95 单测 | **原样复用** |
| L2 宿主适配层 | `ruoyi-office/yudao-module-intent` | 约 1.9k 行 Java（含管理台） | **参考改写** |
| L3 业务声明 | `yudao-module-crm-*`（`intent/` + `intent-rules/`） | 7 个意图 ≈ 670 行 | **照格式重写** |
| L4 前端组件 | 前端源码目前在 **宿主仓** `yudao-module-intent/src/main/resources/intent-ui` | SDK 1152 行 JS + 288 行 CSS | **复用，但位置要先挪（见 §5.1）** |
| L5 前端宿主适配 | `ruoyi-office-vben/apps/web-antd/src/views/intent` | 最小 186 行 / 含管理台 1.3k 行 | **参考改写** |

关键判断：**L1 与 L4 是产品，L2 / L3 / L5 是「每个系统各写一遍的胶水」**。迁移设计的目标就是让胶水尽可能薄。

## 3. 必须「参考改写」的清单（宿主适配层）

按「最小可跑」→「生产可用」排序，每项都给了参考文件与要点。**最小集 = 3.1 ~ 3.7，约 400 行。**

### 3.1 pom 依赖（3 行）

```xml
<dependency>
  <groupId>dev.intent</groupId>
  <artifactId>intent-spring-boot-starter</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

前提：私服里有 `dev.intent:*` 与 `dev.pi:pi-ai|pi-agent`（见 §5.3）。
参考：`yudao-server/pom.xml`、`yudao-module-intent/pom.xml`。

### 3.2 身份：`IntentPrincipalProvider`（约 26 行）

参考 `yudao-module-intent/src/main/java/cn/iocoder/yudao/module/intent/framework/bridge/HostPrincipalProvider.java`。
要点：只回答「当前是谁」（userId / tenantId / roles），**不要在这里查角色**——目录查询是高频调用，查库会拖慢。

### 3.3 权限：`IntentPermissionPolicy`（约 32 行）

参考 `.../framework/bridge/HostPermissionPolicy.java`。
要点：角色判定走宿主自己的权限服务（yudao 走 `PermissionCommonApi.hasAnyRoles`），这样数据权限、角色继承、租户隔离的口径与系统其它模块完全一致。目标系统用 Sa-Token / Shiro / 自研都只影响这一个类。

### 3.4 上下文桥：`IntentContextBridge`（约 82 行）——**最容易漏，漏了会偶发越权**

参考 `.../framework/bridge/HostContextBridge.java`。
要点：pi-agent 的执行循环用 `ForkJoinPool` 跑工具调用（**独立线程**），而数据权限 / 租户隔离 / 登录用户解析依赖线程上下文（Spring Security、TenantContextHolder、RequestContextHolder）。必须在 HTTP 线程捕获、在每个工具线程恢复、执行完还原。
新系统如果是 Servlet + 线程上下文模型，这一层等价物必须写；如果是纯无状态（每工具显式传用户），可以退化为「显式传参」。

### 3.5 执行装配（约 200 行）

参考 `yudao-module-intent/.../framework/config/IntentAutoConfiguration.java`。
**重要事实**：`intent-spring-boot-starter` 只自动装配了 6 个 Bean —— 三个 SPI 默认实现 + 两个仓储（`IntentSpecRepository` / `IntentConfigRepository`）+ 规则增强器。以下仍需宿主自己装配：

- `HostToolRegistry`：收集容器内所有 `IntentTool` Bean；
- classpath `intent-rules/*.yaml` 版 `IntentCatalogEnricher`；
- `ExecutorProfileRegistry`（可选，用「执行器档案」才需要）；
- `TraceStore`（JSONL 目录 / 内存）；
- `IntentRuntime`：LLM 配置 + 工具 + Spec 仓库 + 执行器 + 留痕。LLM 供应商分支见 `buildLlm`（deepseek / openai / anthropic / 自定义 OpenAI 兼容端点），Key 缺省回退环境变量。

### 3.6 HTTP API（约 290 行，3 个控制器）

参考 `.../controller/admin/IntentController.java`、`IntentConfigController.java`、`ExecutorProfileController.java`。
端点：`GET /catalog`（按当前用户角色过滤 + 目录增强）、`POST /execute`（缺参返回 `NEED_INPUT` + 参数 Schema）、`GET /history`、`GET /trace/{traceId}`、`POST /feedback`、`GET /status`；后两个控制器是管理台（意图配置 / 执行器档案）用的。
**注意**：SDK 仓没有 web 层，这块必须自己搬（也是建议下沉的一块，见 §5.2）。前端 SDK 通过 `apiPrefix` 定位接口，新系统换个前缀即可（当前是 `/admin-api/intent`）。

### 3.7 静态资源映射（约 18 行）

参考 `.../framework/config/IntentUiConfiguration.java`：`/intent-ui/**` → `classpath:/intent-ui/`。
同时把 `/intent-ui/**` 加进宿主的安全放行白名单（参考 `yudao-server/src/main/resources/application-local.yaml` 的 `yudao.security.permit-all_urls`）——演示页免登录，但 API 仍需认证。

### 3.8 持久化（可选，约 150 行 + 3 张表）

参考 `.../service/spec/IntentSpecRegistry.java`、`.../service/executor/ExecutorProfileRegistry.java`、`.../dal/mysql/*.java`。
用了它，意图才能后台增删改、保存后即时生效；不用就停在 MEMORY / FILE 模式（种子 YAML，重启还原）。

### 3.9 配置项（约 70 行 + YAML）

参考 `.../framework/config/IntentProperties.java` 与 `application-local.yaml` 的 `intent:` 段：
`enabled` / `system-name` / `time-zone` / `rules-dir` / `llm.*` / `trace.dir` / `suggestions.*` / `gateway.*`。
注意：starter 的 `intent.host.*`（storage / spec-dir / config-dir / rule-dir / trace-dir / rules-enabled / validate-rules）是另一套前缀，两套会同时存在，别混。

### 3.10 前端注入点 `sdk.ts`（约 62 行）

参考 `ruoyi-office-vben/apps/web-antd/src/views/intent/sdk.ts`。只做三件事：

- `apiPrefix`：意图接口前缀；
- `authHeaders()`：**每次请求现取** token（宿主刷新 token 后无需重新挂载），需要多租户再加 `tenant-id`；
- `entityOptions`：槽位下拉的候选数据源，指向宿主自己的接口（客户 / 商机 / 合同的 simple-list）；
- `zIndex`：按宿主弹窗层级调（当前 900，压页面之上、antd 弹窗 1000 之下）。

### 3.11 前端页面上下文 `pageContext.ts` + 挂载组件（约 43 + 48 行）

参考 `.../src/views/intent/pageContext.ts`、`.../components/IntentFloating.vue`。
要点：全局挂一次 `mountFloating({ getPage, getContext })`；`getPage` = 当前路由去掉开头斜杠（与 `IntentSpec.pages` 匹配）；业务页面在 `setup` 里调 `registerIntentPageContext('模块/页面', () => ({ customerId: '12' }))` 提供「当前对象」。抽屉开关与渲染状态由 SDK 内部维护，宿主只管「当前页面能提供什么上下文」。

### 3.12 管理台页面（可选，约 1080 行）

参考 `.../views/intent/config/index.vue`（286）、`.../views/intent/executor/index.vue`（595）、`.../src/api/intent/index.ts`（199）、`.../views/intent/center/index.vue`（33）。
不接管理台的话，意图只能靠 YAML 种子 + 重启生效，业务方无法自助配置。

## 4. 业务层：每个意图要写什么（长期工作量，但都是「填表」）

### 4.1 意图规范 IntentSpec（1 份 YAML / 意图）

参考 `yudao-module-crm/yudao-module-crm-server/src/main/resources/intent/crm.customer.followup-plan.yaml`。五要素：

| 要素 | 字段 | 说明 |
| --- | --- | --- |
| 标识 | `id` / `name` / `description` / `version` | 意图身份证 |
| 输入 | `paramsSchema` / `context` | 入参 Schema（前端据此渲染补参表单）+ 需要的页面上下文 |
| 编排 | `promptTemplate` / `tools` / `executor` | 提示词 + 可用工具白名单 + 执行器（缺省走内置推理循环） |
| 输出 | `cardType` | 结果卡片形态（analysis / plan / ...） |
| 治理 | `policy.roles` / `timeoutSeconds` / `maxRetries` | 谁可用、超时、重试 |
| 挂载 | `pages` | 在哪些页面出现（`crm/customer` 这种「模块/页面」标识） |

### 4.2 宿主工具 `IntentTool` Bean（0~N 个 / 意图）

参考 `yudao-module-crm/yudao-module-crm-server/src/main/java/cn/iocoder/yudao/module/crm/intent/CrmIntentConfiguration.java`（316 行 / 约 12 个工具）。
要点：**进程内直调宿主 Service**，权限、数据权限与事务天然沿用宿主系统，无需跨系统权限改造；参数 Schema 用 `Schemas.object(...)` 声明（LLM 看得到）；工具描述要写清「何时用 / 何时别用」。

### 4.3 事实源 + 规则（做「待办与推荐」才需要）

参考 `.../crm/intent/CrmIntentFactProvider.java`（96 行）+ `.../resources/intent-rules/crm-contract-expiring.yaml`（26 行）。
一条规则 = 查询(`dataset`) + 条件(`filter`) + 输出模板(`badge` / `items`) + 参数映射(`params`)。**改文案、改阈值、改挂载页面只动 YAML，零 Java**；写错（意图不存在 / 参数不在入参 Schema 内）会在启动时直接失败，不会静默失效。

### 4.4 前端页面上下文（每个业务页约 5 行）

参考 `ruoyi-office-vben/apps/web-antd/src/views/crm/customer/index.vue` 里的 `registerIntentPageContext`。

## 5. 迁移前必须先补的 4 个缺口（否则会多出隐藏工作量）

### 5.1 前端组件源码还在宿主仓 —— **必须先挪走**

`intent-ui-sdk`（1152 行 JS + 288 行 CSS + d.ts + package.json）现在放在 `ruoyi-office/yudao-module-intent/src/main/resources/intent-ui/`。跨系统时「单一真源」不成立：第二个系统只能复制目录，以后每修一次 UI 要同步两处。
**建议**：把 `intent-ui/` 迁到 `next-agent/intent-ui-sdk/`，发布 npm 包到私服（或先用 `link:` / `file:` 本地依赖）。这是第 0 步。

### 5.2 SDK 没有 web 层 —— HTTP API 要下沉（可选，但强烈建议）

现状：`/catalog`、`/execute`、`/history`、`/feedback`、`/status` 的控制器在宿主里，新系统必须整段搬（§3.6）。
**建议**：在 `next-agent` 增加可选模块 `intent-spring-boot-starter-web`，把「控制器 + 静态资源映射 + `IntentRuntime` / 工具注册表 / LLM 装配」一起下沉。做完后宿主只剩「3 个 SPI + 若干工具 Bean + 意图 YAML」，接入量从约 800 行降到约 150 行。
（先按 §3 搬一遍能立刻见效，但接第二、第三个系统时这笔钱会重复付。）

### 5.3 交付物还是 SNAPSHOT —— 必须走私服

`dev.intent:*` 与 `dev.pi:pi-ai|pi-agent` 目前全是 `0.1.0-SNAPSHOT`，只在开发机 `D:\repository` 里有。迁移必须先把它们发到目标公司私服并打固定版本号（如 `0.4.0`）。
另外 pi-java 源码在 `D:\project\myopensource\pi-agent`：如果目标方不允许引入这个依赖，`intent-sdk-pi` 需要替换——接触点只有 `LlmConnector` / `AgentExecutor` 这一层，换 SDK 不影响其它模块。

### 5.4 版本门槛：JDK 21 + Spring Boot 3.x

`next-agent/pom.xml` 里 `maven.compiler.release=21`，starter 用 Spring Boot 3.4.9、`jakarta.*`。

- 目标系统 Spring Boot 3.x + JDK 17/21 → 直接可用；
- 目标系统 Spring Boot 2.7 / JDK 8 → **先升 JDK 21 再谈**，否则要维护一份 javax 分支，不划算。

好消息：starter 只依赖 `spring-boot-autoconfigure` 与 `spring-context`，不与宿主的 Web / ORM / 鉴权体系冲突，可以干净地共存。

## 8. 风险与避坑

1. **权限必须走宿主服务层**：工具里直接查 DAO 会绕过数据权限 → 越权。参考实现都是调宿主 Service 并传 `getLoginUserId()`。
2. **写操作的三件事**：幂等（同一 `traceId` 重跑不重复写）、审计（谁在什么时候让 AI 写的）、可识别（AI 写的内容加前缀，如参考实现里的「【AI 方案】」，便于回溯与清理）。
3. **线程上下文丢失**：不做 §3.4，会偶发「查不到数据 / 越权 / 租户串」，压测时不容易复现，别省。
4. **输出闸门会重试**：`SubmitResultTool` 校验不过会整体重试，提示词里要明确输出结构与篇幅上限，否则耗时与 token 会翻倍。
5. **时区**：`expiryText`（还剩几天）依赖 `intent.time-zone`，不配就用服务器时区。
6. **耗时预期**：单意图 10~15s 属正常（实测 11.7s / 12.8s、3.6k~4k tokens）。前端必须有「补参表单 + 进度态」，别做成「点了没反应」。
7. **规则校验失败就让服务起不来**：这是刻意设计（静默不出待办是最难排查的故障），迁移时不要改成「打日志继续」。
8. **不要 fork 内核**：改内核会让 95 个单测失效，后续升级要人工 merge。宿主适配层可以随便改。
