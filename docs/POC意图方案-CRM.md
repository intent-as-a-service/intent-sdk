# CRM POC 意图方案（现场演示版）

> 定位：面向客户现场演示的「意图即服务」能力包。
> 目标：覆盖 CRM 全部 8 个业务对象，每个对象 ≥2 条意图；每条意图都有真实数据支撑、有业务动作、有可验证产出。
> 现状基线（代码实测）：已有 **6 个 CRM 意图 + 8 个宿主工具 + 1 条待办规则**；CRM 库已有 18 客户 / 23 商机 / 20 线索 / 23 联系人 / 26 合同 / 32 回款 / 51 跟进 / 14 产品。

## 0. 结论与建议

候选共 **34 条**，按演示价值分三档，建议**只把 P0 放进演示主线**：

| 档位 | 条数 | 用途 |
| --- | --- | --- |
| **P0 演示主线** | 12 | 15 分钟动线走完「线索→客户→商机→合同→回款」+ 写回闭环 |
| **P1 增强** | 12 | 换一个客户/行业也能演示，避免「只有一条路能演」 |
| **P2 备选** | 10 | 统计与产品类，客户追问时再展开 |

**产品判断（重要）**：单个页面挂 **3~5 条**意图最舒服，超过 6 条菜单开始臃肿。所以同一页面下的 P1/P2 意图**不要全量展示**——用「按上下文/角色/数据条件显隐」控制，或放进「AI 推荐下一步」按需出现（见 §5）。

配套工作量：**新增 12 个宿主工具 + 6 条待办规则 + 1 组演示数据补丁**。

## 1. 设计原则

每条意图必须同时满足三条硬标准，否则不进 POC：

1. **有数据支撑**：入口对象在库里必须有真实记录（当前演示库里客户 320/商机 360/合同 390/回款 400 这条链是完整的）。
2. **有业务动作**：输出必须能落到一个动作上（打电话、改阶段、报价、催收、写回 CRM），不是"分析报告"式的空话。
3. **可验证产出**：结果里的数字、日期、金额必须能与 CRM 页面核对上——客户现场会去点开看。

四类价值（演示时交替出现，节奏才好）：

| 类型 | 特征 | 演示作用 |
| --- | --- | --- |
| 判断类 | 打分、分级、风险、概率 | 第一眼有冲击（红黄绿、评分卡） |
| 生成类 | 方案、话术、邮件、时间表 | 体现 AI 的"深度"（长文本、结构清晰） |
| 执行类 | 写回 CRM（跟进记录/备注） | **体现闭环**——演示里最有说服力的一击 |
| 汇总类 | 跨对象聚合（客户 360、今日优先级） | 体现"跨模块打通"，传统系统做不到 |

## 3. P0 演示主线（15 分钟动线）

| 步 | 页面 | 动作 | 意图 | 展示什么 |
| --- | --- | --- | --- | --- |
| 1 | 待办事项 | 点 AI（不用选记录） | 今日跟进优先级 | 「系统知道我今天该干什么」 |
| 2 | 客户列表 | 选中宏图设计院 | 客户健康度诊断 | 红黄绿评级 + 8 维评分（视觉冲击） |
| 3 | 同页 | 同一客户 | 客户 360° 拜访准备 | 5 个模块数据一次汇总（体现打通） |
| 4 | 同页 | 同一客户 | 生成跟进方案 | **写回 CRM** → 现场点开跟进记录看新增条目 |
| 5 | 商机 | 选「宏图·智慧工地」 | 商机推进策略 | 卡点判断 + 三件事清单 |
| 6 | 合同 | 选「宏图年度服务续约合同」 | 续约策略 | 2 天后到期 → 时间表 + 话术 |
| 7 | 回款 | 选一笔逾期回款 | 逾期风险预警 | 分级动作（电话/函件） |
| 8 | AI 抽屉 | 执行历史 → 点开某次 | —（留痕） | 步骤级留痕、耗时、token（体现可控可审计） |

**收尾话术**：这 8 步里，第 4 步写回是"AI 真的进了业务系统"，第 8 步留痕是"出了问题能查、能回放"——这两点决定客户敢不敢真用。

## 5. 待办与推荐规则（个性化意图描述）

现有 1 条（合同到期）。建议新增 6 条，把「待办数字」翻译成「意图语言」：

| 规则 | 数据源（宿主既有查询） | 展示文案 | 一键动作 |
| --- | --- | --- | --- |
| 客户超期未联系 | `getFollowCustomerCount` | 「N 位客户超过 14 天未联系」 | 客户健康度诊断 |
| 今日需联系 | `getTodayContactCustomerCount` | 「今天有 N 位客户待联系」 | 今日跟进优先级 |
| 商机停滞 | 商机列表（阶段 + 停留时长） | 「N 个商机在方案制定停留超 30 天」 | 商机推进策略 |
| 回款计划到期 | `getReceivablePlanRemindCount` | 「N 笔回款计划已到期未回款」 | 逾期风险预警 |
| 合同待审核 | `getAuditContractCount` | 「N 份合同待我审批」 | 合同审批预检 |
| 线索待跟进 | `getFollowClueCount` | 「N 条线索超过 7 天未跟进」 | 线索质量评分 |

**关键**：规则里的 `params` 直接把 `id` 映射进意图入参，用户点一下就是"带参直接执行"，不需要再选记录——这是这套设计最像"AI 助手"的地方。

## 6. 演示数据方案（真实、闭环、可保鲜）

### 6.1 现有数据体检（实测）

| 问题 | 事实 | 影响 |
| --- | --- | --- |
| 合同审批状态非法 | 合同 380~389 的 `audit_status=2`；而枚举只有 0/10/20/30/40（`CrmAuditStatusEnum`） | 待办口径取不到这些合同，页面显示异常状态 |
| 回款计划缺数据 | `crm_receivable_plan` 只有 5 条，全是 2024 年的旧数据，未挂到新合同链 400~411 | 「回款计划提醒」规则演示不出效果 |
| 跟进记录只覆盖客户 | 51 条跟进里 `biz_type=2`（客户）为主，线索/商机/合同/回款几乎没有 | 写回类意图无处落地，时间线不完整 |
| 商机无停滞样本 | 360~371 的 `update_time` 都很新 | 演示不出「商机停滞」 |
| 无待审核合同 | 合同里没有 `audit_status=10` | 演示不出「合同审批预检」 |
| 客户重名 | id=12 与 id=320 都叫「宏图建筑设计院有限公司」 | 现场选记录会混淆 |
| 日期写死 | 演示链用固定日期，续约合同 390~394 在 2026-09-14 前后到期 | **过期后演示失效** |

### 6.2 要补的数据（全部满足"真实、闭环"）

1. **修复**：合同 380~389 `audit_status` 2 → 20（审核通过），与页面口径一致。
2. **回款计划 12 条**：挂到 400~411，分 1/2/3 期；其中 **3 笔已逾期 5~20 天**、**3 笔 7 天内到期**，金额合计不超过对应合同金额。
3. **跟进记录 18 条**：覆盖 线索(1)/商机(4)/合同(5)/回款(7) 各 3~6 条，内容与各对象时间线自洽（如线索 300 的"初次电话沟通"要能对上）。
4. **2 个停滞商机**：360（宏图·智慧工地，阶段=方案制定，停留 35 天）、364（华宇置业，方案制定，停留 42 天）。
5. **2 份待审核合同**：新增挂 320/322，`audit_status=10`，金额与在手商机一致。
6. **3 位超期未联系客户**：320/321/327，`contact_last_time` = 18~25 天前，`contact_next_time` 已过期。
7. **客户改名**：id=12 改为「宏图建筑设计院（示例-旧数据）」或直接软删除，消除重名。
8. **保鲜脚本**：所有相对日期用 `NOW() - INTERVAL` 生成，提供可重复执行的 `refresh` 脚本（演示前跑一次即恢复新鲜）。

**闭环校验（写完数据必须能对上）**：

### 10.1 A1 口语别名：用户怎么说，就怎么命中

- **数据链路**：`IntentSpec.aliases`（YAML 种子）→ `intent_spec` 表 → `/intent/catalog` 的 `aliases` 字段 → 前端匹配框。
- **匹配算法**（`intent-ui-sdk.js` 纯函数 `IntentUI.match`，宿主可复用同一口径自测）：
  1. 归一化（大小写、标点）后做 **bigram Dice 相似度**；同时跑一遍"去废话词"（帮我/一下/看看…）后的比对，两路取大；
  2. 包含关系统一按 **覆盖比例打折**（`0.85 × 短/长`）。不能给固定高分，否则"这客户咋样了"去掉废话词只剩"客户"，
     所有客户类意图并列 0.85，搜索变成一锅粥；

  4. 阈值 0.34，最多给 8 个候选。

## 11. 第三轮迭代（2026-09-14 晚）：切页即清空，面板永远只讲"当前页面"

演示时暴露的问题：在 A 页面执行完意图、结果卡片还挂在面板上，切到 B 页面后面板里仍是 A 页面的结果与意图列表，
看起来像"AI 在别的页面上乱答"。本轮把「切页」定义成一次彻底的上下文重置。

### 11.1 行为定义（现在的规则）

| 时机 | 面板表现 |
| --- | --- |
| 同一页内重复执行 / 重开抽屉 | 保留上一次结果（同页上下文没变，保留才有用） |
| 切到另一个页面（含 SPA 路由切换） | **结果卡片、下一步、待办分组、补参弹窗、口语输入全部清空**，只显示新页面的意图 |
| 切页后目录还没回来 | 显示「意图加载中…」，不闪"该页面暂未配置意图"，也不残留上一页列表 |
| 切页后目录加载失败 | 显示「意图目录加载失败：原因」，不再静默沿用上一页列表 |
| 执行中途切页 | 上一页在途的执行回包**直接丢弃**，不会落到新页面上 |

### 11.2 实现要点（三处，都在 SDK 里，宿主只接一条路由）

1. `resetPageState(h)`：清空页面级状态（result/currentEntry/error/展开态/口语输入/补参弹窗），
   并 `runToken++` 让上一页在途的执行回包失效；**目录与待办也一起清**，避免回包失败时露出上一页的列表。
2. `Panel.load()`：自己判断"页码是否变化"，变了就先清理并立刻重绘（不等网络），再按新页面拉目录。
   任何调用方（宿主 `reload()`、抽屉打开、调试台）都自动获得同一套语义，不需要各自判断。
3. 宿主 `IntentFloating.vue`：`watch(route.path)` → `floating.reload()`，
   保证"抽屉开着的时候换页面"也会立刻清空，而不是等下次点开。

### 12.8 本轮顺带修掉的两个缺陷（都会让演示「看起来是坏的」）

#### 缺陷一：事实包里的 null 让工具直接失败（SDK 层）

- **现象**：客户 12（无任何跟进记录）跑健康度诊断，`crm_customer_facts` 连续 3 次返回
  `java.lang.NullPointerException`，模型只敢给「数据源故障、7/8 维度数据不足、拒绝打分」。
- **根因**：`intent-sdk-core` 的 `IntentToolResult` 用 `Map.copyOf(data)` 收口结构化明细，
  而 `Map.copyOf` 遇到 **null 值** 会抛无消息的 NPE——`lastFollowUpTime`（没有跟进记录时为空）
  正好是合法业务值。
- **修复**：`intent-sdk-core/src/main/java/dev/intent/sdk/tool/IntentToolResult.java`
  改为「保留 null 的不可变副本」（`Collections.unmodifiableMap(new LinkedHashMap<>(data))`）。
- **影响面**：不是个例——任何「业务事实天然可能为空」的意图都会中招（无跟进、无合同、无回款）。

#### 缺陷二：「按客户取数」其实取的是「我负责的全部」（宿主层）

- **现象**：客户 12 的健康度诊断报出「在手商机 5 个、合计 77.15 万」，实际该客户 **0 个商机**；
  这 5 条分别是朗润医疗、宏图设计院（320）、盛世传媒、蓝海便利、百味食品的商机。
- **根因**：`CrmBusinessMapper.selectPage(VO, userId)` 与 `CrmReceivableMapper.selectPage(VO, userId)`
  的入参 VO 里声明了 `customerId`（`@Schema(description = "客户编号")`），但拼查询条件时**漏了这一条**，
  参数静默失效——调用方以为按客户过滤了，其实拿的是整个用户的数据。合同、回款计划两条链路没这个问题。
- **修复**：两处 Mapper 各补一行 `.eqIfPresent(XxxDO::getCustomerId, pageReqVO.getCustomerId())`。

### 12.10 修掉 pi 内核的并发缺陷：流式追加 vs 快照复制

**现象**：偶发 `java.util.ConcurrentModificationException`，日志 `AgentExecutor - [intent] 推理循环异常中断`，
该次意图直接失败——用户看到的是「AI 偶尔抽风」。多意图并发执行时概率更高。

**根因**（栈：`AssistantMessage.copy` ← `AgentLoop.streamAssistantResponse`）：

```
Provider I/O 线程 ──► output.content.add(...) / set(...)   // 每个 delta 改一次（改 modCount）
Agent 循环线程   ──► partial.copy() ──► for (ContentPart p : content)  // 遍历中检查 modCount → CME
```

适配器把**同一个可变实例**推进事件流，消费线程又要对它取快照，而 `content` 是普通 `ArrayList`——
契约上写着「copy() 用于边流式变更边取快照」，实现上却没有线程安全保证。

**修法**：`pi-ai` 的 `AssistantMessage.content` 改为 `CopyOnWriteArrayList`。迭代即拿快照，
边写边读天然免疫；单条消息的分片数只有 1~3 个，写时复制的成本可忽略。类型与语义不变，
所有消费方（`copy()` / `toolCalls()` / `text()` / Web UI / 会话持久化）无需改动。

**修复文件**

- `pi-java/pi-ai/src/main/java/dev/pi/ai/AssistantMessage.java`（`content` 容器 + 并发契约注释）
- `pi-java/pi-ai/src/test/java/dev/pi/ai/AssistantMessageCopyConcurrencyTest.java`（新增回归用例）

**验证（先红后绿）**

| 层次 | 结果 |
| --- | --- |
| 单元用例（新增） | 一边按真实流式节奏 `add`/`set`，一边循环 `copy()`：**修复前 0.06s 抛 CME，修复后通过** |
| `pi-ai` | **118/118 通过**（含 6 个 Provider 适配器的流式解析测试） |
| `pi-agent` | **44/44 通过**（`AgentLoop` 直接消费方） |
| pi-java 全量 | 15 个模块 `BUILD SUCCESS`（pi-server / pi-coding-agent / pi-subagents / pi-web-ui 等全通过） |
| 宿主并发压测 | 6 个流式意图同时执行：5 个 SUCCESS（第 6 个是我漏传 `contractId` 的用例，返回 NEED_INPUT 属正确行为），日志 **0 次 CME** |
| 意图全量回归 | **69/69 PASS**，整段日志 0 次「推理循环异常中断」 |

**同类遗留（本轮未改）**：`OpenAiResponses` 适配器用 `arguments.put(...)` **就地**改 `ToolCall.arguments`，
理论上会与 `ToolCall.copy()` 里的 `LinkedHashMap` 复制竞争；我们使用的 `openai-completions`（DeepSeek）
路径是整体替换（`arguments = parse(...)`），不受影响。
