# 本体与知识库防腐层（ACL）设计 + yudao 接入验证方案

> 配套图：`docs/diagrams/06-本体与知识库防腐层接入架构.svg` / `.png`
> 配套代码草案：`docs/draft-acl/`（`Ontology.java`、`Ontologies.java`、`KnowledgeBase.java`、
> `KnowledgeBases.java`、`KnowledgeException.java`）
>
> 目标：**先抽象防腐层，再用 yudao 的真实本体/知识库验证它**。
> 验证的标准是：意图层代码在换掉 yudao 之后**一行都不用改**。

---

## 0. 设计要点（四句话）

1. **两个能力端口，一个收口方向**：`Ontology` 与 `KnowledgeBase` 都由**意图 SDK 定义**（抽象一端），
   由**适配器实现**（实现一端）。这是**依赖倒置**：主循环依赖抽象，外部系统提供实现。
   外部术语（collection / embedding / rerank / asset urn / glossary）**到适配器为止**。
2. **能力工具由端口构造，与业务工具彻底分开**：SDK 拿端口构造出内置能力工具
   （`knowledge_search` / `describe_entity` / `resolve_entity`），装进**独立的 `CapabilityTools` 注册表**。
   **业务工具受 `IntentSpec.tools` 白名单管辖，能力工具不受**——租户不该能通过白名单
   把自己配成"不能检索知识库"。
3. **本体是增强项，不是前置依赖**：`Ontologies.empty()` 时全部校验放行，
   行为与接入前完全一致。这样"客户没建本体"不会阻塞上线。
4. **数据型端口可工具化，约束型端口必须有确定性出口**：
   知识库是**数据富化** → 适合做成工具（模型按需检索）；
   实体校验/参数枚举是**约束** → 必须有确定性通道（不依赖模型配合）。
   两个通道共用同一份适配器实现，见 §2.4。

---

## 1. 为什么必须是双向防腐（而不是单向包装）

很多实现把"知识库"做成一个单向的 `retrieve()` 就结束了。这里需要**双向**，因为意图执行既要**读**也要**约束**：

| 方向 | 做什么 | 落在哪 |
|---|---|---|
| **读**（知识 → 模型） | 把外部知识变成可进上下文的片段 | `KnowledgeBase.retrieve()` |
| **约束**（本体 → 参数） | 把实体合法性变成 JSON Schema 的 `enum`，**让模型只能从合法值里选** | `Ontology.candidateValues()` |
| **校验**（本体 → 准入） | 执行前验实体 ID，拦住编造 | `Ontology.validate()` |
| **推导**（本体 → 编排） | 实体关系 → 工具链/流程建议 | `Ontology.relations()` |

**关键判断**：`validate()` 放在 **ACL + `IntentRuntime`**，**不是**做成模型可选的工具。
因为"参数合法性"是**执行前准入检查**，与现有的 `MISSING_PARAMS` / `VALIDATION_ERROR` 同一层。
做成工具 = 让模型自己决定要不要守规矩，逻辑上不成立。

## 2. 接口设计要点

### 2.1 `KnowledgeBase`：三个概念收敛所有形态

```java
public interface KnowledgeBase {
    boolean supports(String kb);                                  // 多实现按 kb 分派
    List<Chunk> retrieve(String kb, String query, int topK);
}
```

- **`kb` 是唯一标识**：可以映射到 yudao 的知识库 ID、Dify 的 dataset name、Milvus 的 collection。
  适配器负责翻译，意图档案里只写 `kb: 1001` 或 `kb: dify-prod`。
- **`Chunk` 带 `ref`**：`title / docId / uri / kb / entity` 五个约定键，
  支撑"数据来源展示"（功能清单 F3.4）与可追溯。**`entity` 键是本体与知识库的联动点**。
- **失败必须抛 `KnowledgeException`，不许返回空**：静默空结果会让模型把"没检索到"
  误判为"确实没有"，这是最危险的失败模式。这与 `FlowExecutor.runKnowledgeNode`
  现有的"未装配检索器即报错"行为一致。
- **`score` 语义**：越大越相关，量纲由实现自定但须单调可比；无分数返回 `null`。

### 2.2 `Ontology`：三个只读概念，服务三个非模型消费者

```java
public interface Ontology {
    boolean supports(String entityType);
    Optional<EntityType> entityType(String entityType);   // 字段/类型/枚举/外键
    List<Relation> relations(String entityType);          // 工具链推导
    List<String> candidateValues(String entityType, int limit);  // → 注入 enum
    Validation validate(String entityType, String id);    // → 准入校验
}
```

- **`candidateValues` 返回空 = "不可枚举"**，调用方据此回退到 `resolve_entity` 两步消解。
  **注意：不能因为返回空就注入空 enum** —— 那等于放弃约束。
- **`validate` 在无本体覆盖时放行**（unknown ≠ invalid），由 `Ontologies` 统一保证。
- **`EntityRef` 用 `type:id` 编码**，可直接放进 `Chunk.ref().get("entity")`，
  这是"按对象过滤检索"的实现基础。

### 2.3 两个注册表：`KnowledgeBases` / `Ontologies`

形态完全对称：持有一组实现 → 按标识分派 → **未命中时语义明确**
（`KnowledgeBases` 抛异常；`Ontologies` 放行）。这个不对称是**刻意的**：
检索不到实现说明配置错了，必须炸；本体没覆盖说明客户没建，应该放行。

### 2.3b 三个概念必须分清（易混，单独列出）

架构里有三个层次，位置和管辖范围都不同：

| 概念 | 是什么 | 谁提供 | 受 `IntentSpec.tools` 白名单管辖？ |
|---|---|---|---|
| **能力端口** `KnowledgeBase` / `Ontology` | 抽象契约（依赖倒置的"抽象"一端） | **意图 SDK 定义** | 不适用（它不是工具） |
| **能力工具** `knowledge_search` / `describe_entity` / … | 由端口构造的内置工具 | **意图 SDK 提供** | **不受管辖**（进 `CapabilityTools`） |
| **业务工具** `crm_get_customer` / … | 宿主业务能力的包装 | **宿主实现** | **受管辖**（进 `HostToolRegistry`） |

装配上有**两个独立注册表**，`AgentExecutor` 在循环里合并后一并给模型：

```java
// 装配（宿主侧）
HostToolRegistry hostTools   = ...;                    // 业务工具：受意图白名单收窄
CapabilityTools  capabilities = CapabilityTools.builder()
        .knowledgeBases(knowledgeBases)                 // → 构造 knowledge_search
        .ontologies(ontologies)                         // → 构造 describe_entity / resolve_entity
        .build();                                       // 能力工具：永远可用

// 主循环（AgentExecutor）
List<AgentTool> loopTools = concat(
        resolveBusinessTools(spec, hostTools),          // 执行器上限 ∩ 意图白名单
        capabilities.tools());                          // 不受白名单影响
```

**为什么要分开**：`IntentSpec.tools` 是**最小权限**机制，语义是"这个意图最多能用哪些业务工具"。
把能力工具混进同一个白名单，会出现"意图忘声明 `knowledge_search` → 该意图静默失去检索能力"
这种难以排查的故障。分开后，检索能力是**平台能力**，由装配决定而不是由每个意图决定。

### 2.4 两个通道：数据型 vs 约束型

这条区分是**本体和知识库在控制流上不一样**造成的：

| | 知识库（数据型） | 本体（约束型） |
|---|---|---|
| 本质 | 数据富化 | 约束与结构 |
| 做成工具？ | ✅ 适合（模型决定查什么、查几次） | ⚠️ 部分适合 |
| 确定性出口 | `flow` 的 `knowledge` 节点（**必须发生**的检索） | 参数 `enum` 注入 + 执行前 `validate()` |

本体拆开看，只有探索型访问适合工具化：

| 本体内容 | 形态 |
|---|---|
| `describe_entity`（这实体有哪些字段） | ✅ 内置工具 |
| `query_relations`（客户 → 合同） | ✅ 内置工具（也供编排层推导工具链） |
| `resolve_entity`（模糊找候选） | ✅ 内置工具（候选太多时的两步消解） |
| **实体 ID 合法性校验** | ❌ **不做工具**。走参数 `enum` 注入 + 执行前 `validate()` |

**判据**：约束必须在**模型生成之前或参数进入执行之前**生效，不能靠模型自觉调用。
把校验做成工具 = 模型可以选择不调 = 拦不住编造 ID。

## 3. yudao 接入验证方案

验证要证明一件事：**意图层不依赖 yudao**。所以验证分两轮，第二轮故意换掉实现。

### 3.1 第一轮：接真实 yudao

#### 知识库适配器（约 15 行）

```java
@Component
public class YudaoKnowledgeAdapter implements KnowledgeBase {

    @Resource
    private AiKnowledgeSegmentService segmentService;   // yudao 既有 Service，不新建

    @Override
    public boolean supports(String kb) {
        return kb != null && kb.chars().allMatch(Character::isDigit);  // 纯数字 = yudao 知识库 ID
    }

    @Override
    public List<Chunk> retrieve(String kb, String query, int topK) {
        try {
            AiKnowledgeSegmentSearchReqBO req = new AiKnowledgeSegmentSearchReqBO()
                    .setKnowledgeId(Long.valueOf(kb))
                    .setContent(query)
                    .setTopK(topK);
            return segmentService.searchKnowledgeSegment(req).stream()
                    .map(doc -> new Chunk(doc.getContent(), doc.getScore(),
                            Map.of(Refs.KB, kb, Refs.DOC_ID, String.valueOf(doc.getDocumentId())),
                            Map.of("source", "yudao")))
                    .toList();
        } catch (Exception e) {
            throw new KnowledgeException(kb, "yudao 知识库检索失败: " + e.getMessage(), e);
        }
    }
}
```

**复用而不是自建**（`AiKnowledgeSegmentServiceImpl` 已提供向量检索 + DashScope rerank +
按知识库过滤 + topK/阈值，且支持 7 家 Embedding 模型与 4 种 VectorStore）。
**且因为走宿主 Service，租户隔离与数据权限自动生效**（同线程，见 `ThreadLocal` 纪律那份文档）。

> 字段名需按 `AiKnowledgeSegmentSearchRespBO` 实际定义核对（`service/knowledge/bo/` 下）。

#### 本体适配器

本体这侧 yudao **没有现成的统一元数据服务**（已确认：`AiToolDO` 是 Spring AI 工具定义，
不是实体元数据；没有实体类型/关系模型）。所以第一轮验证用**最小可用形态**：

**方案 A（推荐，验证成本最低）——复用实体候选机制**
yudao 的"实体槽位自动带出候选"（`集成交付指南.md:232` 记载：`customerId` 的 ⚙ 表单
自动带出 18 个客户候选）已经有一条**真实可用的实体查询链路**。
把它包成 `Ontology`：

```java
@Override
public List<String> candidateValues(String entityType, int limit) {
    // 复用既有实体候选查询（与前端实体下拉同一数据源）
    return entityCandidateService.listCandidates(entityType, limit).stream()
            .map(EntityCandidate::getId).toList();
}

@Override
public Validation validate(String entityType, String id) {
    try {
        return entityCandidateService.exists(entityType, id)   // 宿主既有校验
                ? Validation.ok(new EntityRef(entityType, id))
                : Validation.invalid("实体不存在或无权访问: " + entityType + ":" + id);
    } catch (Exception e) {
        // 校验服务异常 = 未知，不阻塞（避免本体故障拖垮意图执行）
        return Validation.ok(new EntityRef(entityType, id));
    }
}
```

**方案 B——用 `IntentFactProvider` 的现有数据集**
`intent-sdk-host` 的 `IntentFactProvider` 已经能从宿主取"事实行"
（`crm.expiring-contracts` 这类 dataset）。把 dataset 当实体源，
`candidateValues` = `facts.rows(dataset, ctx, limit)` 取主键。**零新增宿主代码**。

### 3.2 第二轮：换掉实现验证防腐层（关键）

**这才是防腐层的验收标准。** 第一轮跑通后，写一个测试把 yudao 换掉：

```java
// 换成一个内存假实现 —— 意图层代码零改动
Ontologies ontologies = new Ontologies(List.of(new InMemoryOntology(Map.of(
        "Customer", new EntityType("Customer", "客户", List.of(
                new EntityField("id", "编号", "string", true, null, null),
                new EntityField("level", "等级", "string", false, null, List.of("A", "B", "C"))))))));
KnowledgeBases knowledge = new KnowledgeBases(List.of(new InMemoryKnowledgeBase(...)));
```

**断言**：`IntentRuntime` / `AgentExecutor` / `FlowExecutor` **一行未改**，
意图 YAML 只把 `kb: 1001` 改成 `kb: fake-kb`，执行结果结构不变。

> 若第二轮需要改意图 SDK 的任何代码，就说明防腐层漏了 —— 这是设计缺陷的信号，不是测试问题。

### 3.3 验证矩阵

| # | 验证点 | 通过标准 |
|---|---|---|
| V1 | 知识库检索走通 | `kb: <yudao知识库ID>` 的 flow 节点返回真实片段，`ref.docId` 有值 |
| V2 | 检索失败不静默 | 知识库不存在 → `TOOL_ERROR`，**不是**空结果 |
| V3 | 候选值注入 enum | 参数 Schema 里 `customerId` 出现 `enum`，模型只能从候选中选 |
| V4 | 实体校验拦编造 | 传 `C-99999` → `VALIDATION_ERROR`（或 `NEED_INPUT`），不进执行循环 |
| V5 | 无本体放行 | `Ontologies.empty()` 时同上参数**正常执行**，行为与接入前一致 |
| V6 | 租户隔离自动生效 | 切换到租户 B，检索/校验**只能看到 B 的数据**（验证同线程上下文生效） |
| V7 | 多实现并存 | 同时注册 yudao 与一个外部假实现，按 `kb` 正确分派 |
| V8 | **换实现零改动** | §3.2 第二轮：意图 SDK 零改动 |

## 4. 两个容易做错的地方（提前指出）

### 4.1 `candidateValues` 返回空时不能注入空 enum

```java
// ❌ 错误：候选不可枚举时注入空 enum，模型无值可选
schema.put("enum", candidateValues);

// ✅ 正确：空 = 不可枚举 → 不注入 enum，改用 resolve_entity 两步消解
List<String> candidates = ontologies.candidateValues("Customer", 20);
if (!candidates.isEmpty()) {
    schema.put("enum", candidates);
}
```

但要注意一个**隐蔽陷阱**：`Enum.isEmpty()` 与"没有候选"**语义不同**。
若客户确实一个候选都没有（空集），注入 `enum: []` 是对的（模型什么都不该选），
而"候选不可枚举"才是不注入。建议把返回类型改成**三态**而不是裸 `List`：

```java
record Candidates(boolean enumerable, List<String> values) { ... }
```

### 4.2 本体校验失败不要抛异常，要回传模型自纠

`Ontology.validate()` 失败时，走 `NEED_INPUT` 或把原因作为工具错误回传模型
（与 `SubmitResultTool` 现有做法一致：`IntentToolResult.error(...)` 让模型修正后重试），
**不要直接抛 `IllegalStateException`** —— 那会被 `IntentRuntime` 归到 `VALIDATION_ERROR`
并终止执行，用户看到的是失败而不是"请确认你要操作哪个客户"。

### 4.3 知识库 chunk 长度要截断

`Chunk.content` 直接拼进提示词，若不截断，一个长文档片段可能吃掉整个上下文预算。
建议在**适配器侧**限制单 chunk 上限（如 2000 字符），而不是让意图层兜底 ——
因为不同知识库的 chunk 粒度差异极大（yudao 按 token 切，Dify 按分隔符切）。

## 5. 落地顺序

| 步骤 | 内容 | 工作量 | 产出 |
|---|---|---|---|
| A1 | 把 `docs/draft-acl/` 的 5 个接口挪进 `intent-sdk-core/.../acl/` | 0.5 人日 | 编译通过 |
| A2 | 新增 `CapabilityTools`（由端口构造内置工具）+ `IntentRuntimeConfig` 增加 `knowledgeBases()` / `ontologies()` / `capabilityTools()` 装配位 | 0.5 人日 | 装配可用 |
| A3 | 打通确定性检索：`FlowExecutor.runKnowledgeNode` 改用 `KnowledgeBases`（替换现在的 `List<KnowledgeRetriever>`） | 0.5 人日 | V1/V2 |
| A4 | `AgentExecutor` 合并两套注册表 + **能力工具不进意图白名单**（关键：防止被 `IntentSpec.tools` 收窄） | 0.5 人日 | 能力工具恒可用 |
| A5 | `AgentExecutor` 注入候选 enum + 执行前校验（约束型端口的确定性出口） | 1 人日 | V3/V4/V5 |
| A6 | `YudaoKnowledgeAdapter` + `YudaoOntologyAdapter`（方案 A 或 B） | 1 人日 | V6 |
| A7 | `InMemory*` 假实现 + 换实现测试 | 0.5 人日 | V7/V8 |

**合计约 4.5 人日**，其中 A1~A3 是纯机械工作。

> A4 容易被漏。若图省事把能力工具直接塞进 `HostToolRegistry`，
> 会因为 `IntentSpec.tools` 默认空 = "全部已注册工具"（`AgentExecutor.resolveTools`）
> 而**碰巧能用**；但一旦某个意图显式声明了 `tools:` 白名单（生产环境必然会发生），
> 该意图就会**静默失去检索能力**。必须分开注册表。

## 6. 与既有代码的衔接（不要重复造）

| 现有 | 处理 |
|---|---|
| `KnowledgeRetriever`（`intent-sdk-core/.../executor/`） | **被 `KnowledgeBase` 取代**。它现在只有测试桩实现、且 `ExecutorProfile.knowledge` 被构建期拒绝，替换成本低 |
| `FlowExecutor` 的 `retrievers` 字段与 `runKnowledgeNode` | 改为持有 `KnowledgeBases`（行为不变，只是分派方式统一） |
| `ExecutorProfile.knowledge`（`List<KnowledgeRef>`） | **解禁**（`ExecutorProfiles.java:72-74` 删掉那条拒绝），agent 型据此在系统提示词前置检索注入 |
| `AgentExecutor.buildSystemPrompt` | 增加"检索片段"与"实体约束说明"两段——这是 A4 的落点 |
| `JsonSchemaValidator` | 校验前先做实体校验（A4） |
